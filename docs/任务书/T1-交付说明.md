## 二、两个关键实现点（答辩要讲这两句）

### 2.1 防超售：一条 SQL 决定成败

```sql
UPDATE hotel_room_daily_rate SET sold_inventory = sold_inventory + #{count}
WHERE room_type_id = ? AND biz_date = ? AND deleted = b'0'
  AND sold_inventory + #{count} <= total_inventory
```

影响行数为 0 即抛 `ERROR_HOLD_FAILED (1003004221)`，**全程没有「先查再写」**。
`createHold` 的「总库存 − 已售 − 有效占位」只是预检，强一致兜底在 `submit` 的原子更新上；
未排房的日期首次售卖走 P0 的兜底插入。占位过期由 `@Scheduled(0 */5 * * * ?)` 置 `40 已过期`。

### 2.2 智能定价：可解释 + 能回测 + 诚实

```
建议价 = 基线价 × 出租率系数 × 提前期系数 × 周末系数，夹在 [0.7x, 1.5x]，取整到元
```

- 出租率系数：<40% → 0.85；40~70% → 1.0；70~85% → 1.15；>85% → 1.30
- 提前期系数：>30 天 0.90（早鸟）；<3 天且销量进度 <50% → 0.90（尾房），≥50% → 1.20；其余 1.0
- 周末系数：周五/周六 1.20，法定节假日 1.35（演示用固定节假日表）
- **历史同期无数据时退化用「当前已售进度」判断，并在 reason 里写明，不假装有历史数据**
- reason 是给人看的话，例如：
  `历史同期无出租数据，按当前已售进度 20%，属淡季；距入住 1 天已售 20%，建议下调 23%（¥300 → ¥230）`

**回测诚实性**：需求弹性 `-1.2` 是**行业经验假设值**（代码常量 `DEMAND_ELASTICITY`，注释与接口返回的 `assumption` 字段都写明），
不是本项目数据拟合结果。回测口径：模型统一按「入住前 14 天决策」，逐日算
`原价 RevPAR` 与 `建议价 RevPAR = 建议价 × 出租率 × (新价/原价)^(-1.2)`，再求均值与 `upliftRate`。

> 实测：区间 10/22–10/26（有真实日历数据）`upliftRate ≈ +1.46%`；
> 区间 9/21–10/20（demo 库还没铺历史排房）会按 60% 兜底出租率估算，结果约 -2%。
> 答辩演示请选**有排房数据**的区间，或等 T4 的演示数据生成器铺完历史数据再跑。
