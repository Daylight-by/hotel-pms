# P2 ·「商业化与合规」—— 生态对接与多门店

> 先读 [`00-总纲与派发说明.md`](./00-总纲与派发说明.md) 第 2 节（环境与规范）与第 4 节（通用 DoD）。
> **前置依赖：P0 + P1 均已验收通过**。

## 0. 为什么是这些

P0/P1 解决"能管、能卖"，但一家真实酒店在中国大陆开业还差三样绕不开的东西：

1. **合规**：《旅馆业治安管理办法》要求**旅客住宿登记信息必须实时上传公安机关旅馆业治安管理信息系统**。这是法定强制项，不做就是违法经营。同时前台普遍用身份证读卡器自动录入、用门锁系统发房卡。
2. **分销**：只靠直销拿不到量，必须接携程/美团等 OTA，做库存与订单双向同步。
3. **规模化**：单店跑通后要开分店，要做协议单位挂账（AR 应收），要有报表中心给老板看。

P2 做完 = 这套系统具备商业化交付能力（可以卖给/部署给真实酒店）。

> **重要**：P2 涉及大量外部硬件/厂商接口，本机无法真连。**所有外部对接必须做「适配器 + 模拟器」双实现**，通过配置切换；模拟器默认启用，保证无硬件也能跑通全链路与验收。

> **数据权限**：芋道 RBAC 的 `data_scope` 只支持部门维度。酒店需要**门店维度**。做法：在 `hotel` 的 Service 层统一注入 `StoreContext`（从请求头 `store-id` 或用户默认门店取），所有查询 wrapper 追加 `eq(DO::getStoreId, storeId)`；超管（`storeId=0`）不追加。
> **必须写一个 `HotelStoreInterceptor`** 或 AOP，避免每个方法手写。

## 4. 测试用例

### 4.1 门店与数据权限
1. 创建门店 A、B → 列表可见。
2. 用户切到门店 A 后查房间列表 → **只见 A 的房间**（B 的不可见）。
3. 不带 `store-id` 头时按用户默认门店过滤。
4. 超管（storeId=0）可见全部。
5. 跨门店操作（用 A 的身份改 B 的订单）→ `1003004303`。

### 4.2 公安上传
6. 入住时自动生成 `hotel_psb_upload_log` 一条 `action_type=10`。
7. Mock 模式下该记录 `status=20 成功` 且有回执号。
8. 身份证号校验位错误 → 建档/上传时 `1003004312`。
9. 手动把某条置为失败 → 点重试 → 重新变成功；连续失败 5 次后不再重试且产生告警。
10. 退房 → 新增 `action_type=20` 记录；换房 → `action_type=30`。

### 4.3 门锁
11. 入住 → 发卡日志 `action_type=10`、`status=20`，`valid_to` = 离店日 12:00。
12. 续住 → 续卡日志，`valid_to` 后延。
13. 退房 → 销卡日志。
14. 门锁失败不阻断入住主流程（订单仍成功，仅日志 `status=30`）。

### 4.4 OTA
15. 配置 OTA（mock 开启）→ 点同步订单 → 生成 1 条 `hotel_ota_order` 且本地订单已建。
16. 再次同步同一 OTA 单号 → 幂等跳过，不重复建单。
17. 推价后 `last_sync_time` 更新。

### 4.5 AR 挂账
18. 协议单位额度 10000，挂账 5000 → `used_amount=5000`，账页余额 0 可结账。
19. 再挂账 6000 → `1003004342`。
20. 生成结算单 → 金额等于未结挂账合计；收款 5000 → `status=20 部分收款`；收完 → `30 已结清`，`used_amount` 相应减少。
21. 停用单位挂账 → `1003004343`。

### 4.6 报表与审计
22. 日报返回营业日、OCC、ADR、RevPAR、房费收入、总营收等全部字段且数值自洽。

24. 导出接口返回 xlsx 文件（Content-Type 正确，文件非空）。
25. 冲销操作后 `hotel_operation_log` 新增一条，含 before/after JSON。
