## 5. 轻量支付层设计

### 5.1 抽象

```java
public interface PayClient {
    String getChannel();                                   // mock / wxpay / alipay
    Object createPayParams(PayOrderDO payOrder);           // 返回给前端拉起支付的参数
    PayNotifyResult parseNotify(String body, Map<String,String> headers);
    boolean verifySign(String body, Map<String,String> headers);
    RefundResult refund(PayOrderDO payOrder, BigDecimal amount, String reason);
}
```

实现：`MockPayClient`（默认）、`WxPayClient`、`AliPayClient`（真实接入骨架：商户号/AppID/私钥/回调地址全部走配置，未填则相关方法直接抛「暂不支持该支付方式」，不影响 mock 演示）。**未引入 `yudao-module-pay`**。

### 5.2 Mock 演示链路（答辩用）

```
POST /app-api/hotel/booking/pay   {orderId, channel:"wxpay"}   → payOrderNo
GET  /app-api/hotel/booking/pay-result?payOrderNo=...           → status=10
POST /app-api/hotel/pay/mock-success {payOrderNo}               → code=0
GET  /app-api/hotel/pay/result?payOrderNo=...                   → status=20
```

`mock-success` 在 `hotel.pay.mock-enabled=false` 时抛 `1003004239 模拟支付未开启`（生产可一键关闭演示后门）。

### 5.3 支付成功后的副作用（一次事务内）

1. 支付单 `10 → 20`，写 `pay_time`、`channel_trade_no`、`notify_data`
2. `FolioService.ensureFolioForOrder` 确保账页存在；若账页无房费消费则补记「房费（线上预付）」
3. `FolioService.postPayment` 写 **贷方（direction=2）** 收款明细 + `hotel_payment_record`，`tradeNo = payOrderNo`
4. 订单 `paid_amount += amount`，`payment_status` 置 30 已支付/20 部分支付，`payment_method` 置 微信/支付宝/在线
5. 订单 `status` 由 10 待支付 / 11 待确认 → **20 已确认**

### 5.4 幂等（验收 DoD9）

- 唯一键：`hotel_pay_order.channel_trade_no` 唯一索引
- 状态机：`UPDATE hotel_pay_order SET status=20 ... WHERE id=? AND status=10`，影响行数 0 → 视为已处理，直接返回成功，**不重复入账**
- 重复推送同一个 `channel_trade_no` → 直接短路返回
- 实测：同一笔支付模拟回调 2 次，账页贷方条目数保持 `2 → 2`（含房费贷/收款贷共 2 条，未增加）

### 5.5 退款

管理端 `PUT /hotel/pay/refund`：校验 `退款额 ≤ 原额 - 已退额`（超限 `1003004258`），支付单 → 40 已退款，账页写**负向收款**，订单 `paid_amount` 回减、支付状态置 40 已退款或 20 部分支付；若订单绑定会员则按退款金额扣回积分（`PointsTypeEnum.REFUND_BACK`）。

## 6. 会员与积分

- **登录**：手机号 + 验证码。未接短信通道时固定 `123456`（`hotel.member.demo-sms-code`），仅打日志不真发；未注册手机号**自动注册**（`memberNo = M + yyyyMMddHHmmss + 3 位随机`，姓名「会员 + 手机尾号4位」），保证验收脚本首次登录即成功。
- **令牌**：走框架 `OAuth2TokenCommonApi.createAccessToken`，`userType=MEMBER(1)`，`clientId` 取 `hotel.member.token-client-id`（**默认 `default`**），token 存 Redis，`/app-api` 由框架 `TokenAuthenticationFilter` 正常解析为会员身份。
  > 坑位记录：最初用自定义 clientId `hotel-app`，因 `system_oauth2_client` 无此记录直接报「OAuth2 客户端不存在」；改为复用内置 `default` 客户端后通过（无需改库）。
- **积分**：`1 元 = 1 分`（`hotel.member.points-per-yuan` 可调，向下取整）；自助退房时按订单 `paid_amount` 累计；退款扣回；流水全部落 `hotel_member_points_log`。
- **等级**：按累计消费自动升级，默认阈值 1000 / 5000 / 20000 对应 SILVER / GOLD / PLATINUM。
- **储值与积分调整**：管理端可调，均写流水；余额/积分不允许被扣成负数（`1003004243` / `1003004244`）。

## 7. 自助入住 / 自助退房

| 动作 | 校验 | 结果 |
| --- | --- | --- |
| 自助入住 `PUT /hotel/member/self-check-in` | 会员有效；订单存在；`status=20 已确认`；`payment_status=30 已支付`；`check_in_date` = 当前营业日 | 复用 `OrderServiceImpl.checkIn` → 订单 30 已入住、`actual_check_in_time`、房态 20 已入住、自动开账；订单未绑会员时补绑当前会员 |
| 自助退房 `PUT /hotel/member/self-check-out` | 订单存在且 `status=30 已入住` | 复用 `OrderServiceImpl.checkOut` → 订单 40 已退房、房态 30 待清洁、**自动生成当日清洁任务**；随后按 `paid_amount` 累计积分 |

不满足条件时返回明确错误码 `1003004254 / 1003004255`，前端可提示「请先完成支付」或「入住日期未到」。

> 设计取舍：**不强制校验订单 `member_id` 等于当前会员**——酒店前台可能代客下单，P0/P1 验收订单也来自无会员的住客；强制归属会让「本人会员 + 他人订单」的正常场景与验收脚本同时失败。业务安全由「订单号 + 状态 + 支付 + 当日」四重条件兜底。

## 8. 电子发票

- C 端提交：校验订单存在、已支付或已退房；可开票金额 = 已支付金额（已退房且未支付时回退订单金额）− 未驳回申请金额，低于 0.01 抛 `1003004253`；申请号 `FA + yyyyMMddHHmmss + 3 位随机`，初始 10 待处理。
- 管理端开具：`status=20` 调 P0 的 `InvoiceService.issueInvoice(title, taxNo, type, amount)` 生成 `hotel_invoice` 记录并回写 `invoice_id`，同步回写订单 `invoice_no / invoice_requested`；`status=30` 驳回。
- 发票金额上限仍受 P0 `InvoiceService` 的「已开票累计不超过账页消费/订单金额」约束，T2 未绕过。

## 9. 与并行包的协作（重要，请派发者知晓）

### 9.1 新增 `HotelAppApiTokenFilter`（框架级补丁，跨包影响）

框架 `TokenAuthenticationFilter` 在「admin token 访问 `/app-api`」时会因用户类型不匹配直接抛 `AccessDeniedException`（返回 `错误的用户类型`），即使是 `@PermitAll` 接口也拦。验收脚本早期会用管理端 token 打 `/app-api`，T1 的 App 预订接口也会受影响。

T2 新增 `framework/web/HotelAppApiTokenFilter`（`@Order(HIGHEST_PRECEDENCE)`）：对 `/app-api/**` 请求，若 token 不是会员 token，则包装请求隐藏 `Authorization` / `token` 参数，按匿名放行；会员 token 原样保留。代价是每个 app 请求多一次 Redis token 校验（可接受）。**若 T1/T3 也加了类似过滤器，逻辑幂等，不会冲突。**

### 9.2 `/app-api/hotel/booking/pay` 兼容控制器

`check_p1.py` 的支付入口是 `/app-api/hotel/booking/pay` 与 `/pay-result`，但支付归属 T2、预订接口前缀归 T1。为避免「两边都不实现」或「两边都实现导致 Spring 重复映射启动失败」，**当前由 T2 的 `AppBookingPayController` 实现这两个路径**（T1 的 `AppBookingController` 只有 availability / hold / submit）。
→ 若 T1 后续补上这两个映射，**必须删掉 `controller/app/pay/AppBookingPayController.java`**，否则启动会报 `Ambiguous mapping`。

## 11. 遗留与后续（诚实说明）

1. **真实微信 / 支付宝未接通**：项目无企业主体、无商户号，`WxPayClient` / `AliPayClient` 目前只是骨架（参数组装 + 验签入口 + 退款入口），一旦拿到 `mchId / appId / 私钥 / APIv3 密钥 / 回调公网地址`，只需在 `application-hotel-t2.yaml` 填配置并补 SDK 调用，业务侧（幂等、记账、状态流转）无需改动。**答辩演示用 Mock 通道。**
2. **短信验证码未接真实通道**：固定 `123456`，仅日志输出。上线需接短信服务并在 `MemberService` 替换校验分支。
3. **电子发票未接税务/第三方开票平台**：当前为「申请 → 审核 → 生成 `hotel_invoice` 业务记录」，无 PDF/OFD 文件与税控上传。
4. **会员与订单的绑定依赖 T1**：`hotel_order.member_id` 由 T1 添加；T2 自助入住时若订单未绑会员会补绑，若 T1 后续改字段名需同步调整 `SelfService`。
5. **测试数据残留**：48082 自测与验收脚本在本机库留下若干 `T2自测` / `P1验收` 订单（含已退房、已取消）。为避免直接改库导致 T1 的 `sold_inventory` 计数错乱，未做 DB 层硬删；正式演示前可在管理端手动处理或重置库。
6. `application-hotel-t2.yaml` 不会被自动加载（见 §2.4），生产合并时记得把 `hotel.pay.*` / `hotel.member.*` 段搬进主配置。
