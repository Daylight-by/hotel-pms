# 酒店管理系统 · 功能调研与差距分析

> 调研时间：2026-10-21 ｜ 对象：本仓库 `yudao-module-hotel`（基于芋道 yudao-boot-mini）

## 一、结论

1. **当前形态**：一个"房态 + 订单 + 保洁 + 基础统计"的**前台骨架**，业务闭环能跑通，但离"能卖的系统"还差两条主线——**钱（账务）**和**营业日（夜审）**。
2. **不建议现在公开仓库**。理由见第七节。
3. **补齐优先级**：先补 L2（账务/夜审/房价日历），再补 L4（客户预订端），最后接 L3（合规硬件）与渠道。L3 里的"公安上传"是**法定强制**，一旦真接入客户就绕不开。

---

## 二、覆盖度速览

| 层级 | 定义 | 覆盖 |
|---|---|---|
| L1 前台核心 | 行业公认必备，缺一项前台就得回到手工记账 | 4 / 6 |
| L2 经营必备 | 中小酒店选型必查，决定"能不能卖" | 0 / 6 |
| L3 中国合规 | 不接不能合法营业 | 0 / 5 |
| L4 客户侧 | 面向住客的预订与自助端 | 0 / 4 |

## 三、行业标准：一套 PMS 到底该有什么

### 3.1 通用核心（六项"must-have"）

RateGain、roommaster、Oracle Hospitality 三家的选型口径高度一致，核心只有六块：

| # | 模块 | 具体内容 |
|---|---|---|
| 1 | 预订与前台 | 多渠道预订汇入统一日历、房态图（tape chart）、改期/取消/换房、排房 |
| 2 | 房型与房价 | 房型库存、价格计划（rate plan）、季节性/周末价、连住与限制条件 |
| 3 | 入住与退房 | 证件核验、押金/预授权、房卡、退房结账、房间转脏房 |
| 4 | 账务与夜审 | 客账（folio）、消费挂账、拆账合并、城市账本、**夜审过账 + 营业日切换** |
| 5 | 客房管家 | 干净房/脏房/已查/维修房（OOO）四态、派工、查房 |
| 6 | 报表 | 出租率（Occupancy）、平均房价（ADR）、每间可售房收入（RevPAR）、经理速报 |

**其余都是 situational（按业态选配）**：收益管理 RMS、客人 App、自助机、升级销售、忠诚度、宴会与团队。

### 3.2 商业化必备（国内中小酒店选型会逐条问）

- 房价日历（按日定价，周末价/节假日价/连住价）
- 押金台账与预授权、消费挂账、拆账/合并账、退房结算单
- 夜审 + 交班（班次交接、当日报表锁定）
- 续住、换房、房型升级、**钟点房**、团队/批量锁房
- 超订控制、关房（维修房不参与售卖）
- 发票（纸质/电子）、聚合支付
- 会员/储值/积分、**协议单位 AR 挂账 + 授信额度**
- 渠道（OTA）订单汇入与房量同步

### 3.3 中国本地化：合规与硬件（最容易低估）

| 项 | 性质 | 依据 |
|---|---|---|
| **旅馆业治安管理信息系统上传** | **法定强制** | 《广东省旅馆业治安管理规定》（2025-02-01 施行）第八条要求"安装并使用"；未安装逾期不改罚 5000–10000 元。上海要求**登记后 2 小时内上传** |
| 身份证读卡器 / 人脸核验 | 硬件对接 | 前台实名登记的事实标准 |
| 门锁制卡 | 硬件对接 | 入住写卡、续住延期、退房失效 |
| 电子发票 | 平台对接 | 客人退房即开票 |
| 聚合支付 / 预授权 | 支付通道 | 微信、支付宝、银行卡预授权 |
| 微信小程序订房 | 私域 | 降低 OTA 佣金，行业标配 |

### 3.4 面向客户（C 端）该有什么

官网/小程序预订引擎（日历房、实时房量）、在线支付与担保、在线选房、自助入住机、电子房卡、在线开票、住中服务请求（加枕/送物/报修）。

**两个结论**：
1. GitHub 上 95% 的"酒店管理系统"是毕设/课设，功能停在"房间 CRUD + 订房 + 退房"，**没有一个覆盖账务、夜审、渠道、合规**——所以我们缺的不是代码量，而是这几块业务深度。
2. 真正难的四件事：**账务模型（folio/拆账/挂账）、营业日与夜审、渠道房量同步、本地合规**。这四块恰恰是"看起来简单、做起来最容易翻车"的地方。

## 六、差距清单（按优先级）

### P0 —— 不补就不能开门营业

| 缺口 | 为什么必须 | 工作量判断 |
|---|---|---|
| **营业日 + 夜审** | 酒店按"营业日"结账，不是自然日。没有夜审就无法锁定当日账、无法出日报 | 中 |
| **账务 folio**：押金、消费挂账、拆账/合并、退房结算单 | 现在只有"订单金额 + 已收金额"两个字段，无法处理"押金抵扣 + 微信 + 挂账"的组合结算 | 大 |
| **房价日历** | 现在房间只有一个固定 `price`，无法做周末价/节假日价/连住价，旺季没法调价 | 中 |
| **续住 / 换房 / 钟点房** | 前台每天都在做，缺失只能手工改单 | 中 |
| **超订控制 + 关房** | 现在只有"同房间日期重叠"校验，没有按房型控量 | 小 |
| **收银交班 + 发票** | 前台交接班对不上账；客人退房要发票 | 小–中 |
| **报表指标补全** | ADR / RevPAR / 渠道占比 / 经理速报 | 小 |

### P1 —— 面向客户（你提到的"面向客户"）

| 缺口 | 说明 |
|---|---|
| 客户预订端（小程序 / H5） | 日历房展示、实时房量、下单、支付、订单查询 |
| 在线支付 + 押金 | 微信/支付宝，支付回调驱动订单状态 |
| 在线选房 / 自助入住 | 可选，先做"预填登记 + 到店核验"更现实 |
| 电子发票 | 对接第三方开票平台 |

### P2 —— 商业化与合规

| 缺口 | 说明 |
|---|---|
| **公安上传（强制）** | 各地接口不同（多为省/市局平台或第三方服务商），需要客户提供对接资质 |
| 身份证读卡 / 门锁制卡 | 硬件厂商 SDK，通常按项目对接 |
| OTA 渠道直连 | 携程/美团/飞猪需服务商资质，一般通过 channel manager 间接接入 |
| 会员 / 协议单位 AR 挂账 | 储值、积分、授信额度、月结对账 |
| 多门店 / 集团 | 芋道多租户可承载，但需要门店维度的数据隔离设计 |

## 七、关于"现在要不要公开仓库"

**我的判断：先私有。**

理由：

1. **半成品公开对"面向客户"是负资产**。客户或合作方点进仓库，看到的是没有夜审、没有账务、没有合规对接的版本，第一印象会定格在"玩具项目"，后续再更新也很难翻案。
2. **公开等于把技术路线和实现细节交出去**。这套东西的价值不在 CRUD，而在我们踩过的坑（状态机、房态联动、夜审口径），这些恰恰是可以被直接复制的。
3. **合规风险**。仓库里现在有示例身份证号、手机号等字段与种子数据，公开前需要脱敏；一旦接了公安上传，相关代码更不适合公开。

**如果一定要公开，最低标准**：

- [ ] 明确许可协议（建议 MIT，或商用另授权）
- [ ] README 首屏写清"开发中 / WIP"，列出已实现与未实现，避免误导
- [ ] 移除或脱敏种子数据（身份证、手机号、真实酒店信息）
- [ ] 移除本地配置里的密码、密钥
- [ ] 至少有 1 篇截图 + 1 段 3 分钟演示流程
- [ ] 关键业务规则有文档（状态机、账务口径），否则别人看不懂价值

**替代方案**：私有仓库 + 一个只放"截图 + 功能清单 + 架构说明"的公开仓库（`xxx-showcase`），对外展示、对内保密。这个方案最适合"要拿去谈客户"的场景。

## 八、建议路线（三期）

### 第 1 期：补齐"能开门"（P0）
房价日历 → 账务 folio（押金/挂账/拆账/结算单）→ 夜审与营业日 → 续住/换房/钟点房 → 交班与发票 → 报表指标补全。
**交付标准**：一个真实前台能连续跑完 7 天营业日不出错。

### 第 2 期：面向客户（P1）
预订引擎（小程序/H5）+ 在线支付 + 订单查询 + 电子发票。
**交付标准**：客人能自己下单付款，前台只做核验。

### 第 3 期：商业化（P2）
公安上传、门锁、身份证读卡、OTA 渠道、会员与协议单位 AR、多门店。
**交付标准**：可交付给一家真实酒店试运行。
